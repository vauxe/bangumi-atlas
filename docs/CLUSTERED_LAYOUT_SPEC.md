# 社区分块布局规格

## 1. Context and Goals

当前全局 UMAP 直接把全部连通节点投影到同一个空间。它能保留局部邻接关系，但大型社区彼此穿插，用户难以快速辨认“这一块是什么、它和旁边一块有什么关系”。

本改动新增可选的 `clustered` 布局：先用 Leiden 社区作为视觉分块，再在每块内部保留 UMAP 的局部结构。目标是让节点呈现为边界清楚、内部紧密的块，同时继续输出既有的三维坐标契约。

本阶段保留周更任务的 `umap` 默认值。只有全量数据对比达到验收标准后，才考虑切换默认布局。

## 2. Users and Use Cases

- 探索者需要先看清主要社区，再缩放查看社区内部的作品、人物和角色关系。
- 维护者需要用同一份全量图数据对比 `umap` 与 `clustered`，且不覆盖线上布局产物。
- 发布流程需要继续读取 `x`、`y`、`z`、`community` 字段，不增加前端迁移成本。

## 3. Functional Requirements

1. CLI 增加 `--algo clustered`，现有 `umap` 和 `drl` 行为保持不变。
2. `clustered` 复用全局三维 UMAP 作为块内初始坐标，复用 Leiden membership 作为社区标识。
3. 节点数不少于 200 的社区作为主要视觉块。主要块按节点数分配半径，圆心以该社区在全局 UMAP 投影中的质心为初始位置；确定性的圆形碰撞消解只做消除重叠所需的最小位移，保持主要块的相对方位。
4. 每个主要块内部对原始坐标重新居中和缩放，块内节点保持相对结构，深度继续受全局深度比例约束。
5. 小于阈值的连通社区按社区聚合成外围岛屿；无边节点放在最外层，避免和主要块混在一起。
6. 相同输入必须产生相同的后处理结果。
7. CLI 增加可选 `--output-dir`，默认仍为 `data/layout`，以便对比布局写入独立目录。
8. `report.json` 增加分块数量、主要块覆盖率、投影重叠率、社区近邻保持率和布局后处理耗时；既有报告字段保持兼容。

## 4. Non-Functional Requirements

- 坐标必须为有限的三维浮点数，输出表结构保持兼容。
- 主要块在水平投影中的圆形边界不得重叠，块间保留固定比例的留白。
- 全量数据中，主要块应覆盖至少 90% 的连通节点。
- 基于固定种子的抽样中，投影空间 10 近邻的同社区比例不低于现有 UMAP 基线。
- 主要块圆心的 3 近邻块集合与其全局 UMAP 质心的 3 近邻集合平均保持率不低于 0.6。
- 分块后处理不执行社区间两两节点比较；复杂度以节点数和社区数为主，避免平方级节点开销。
- 全量后处理目标为 60 秒内完成；若未达到，报告实测值并在切换默认值前优化。

## 5. Boundaries and Non-Goals

- 本阶段不修改前端渲染协议，不新增显式社区外框或标签。
- 本阶段不改变周更工作流的默认算法。
- 本阶段不递归拆分超大社区；先验证一级分块能否解决主要可读性问题，再依据指标决定是否增加层级。
- 本阶段不保证所有跨社区边都短。清楚的社区边界优先于跨社区边长最小化。
- 社区是布局分组，不代表人工编辑的主题分类。

## 6. Acceptance Criteria

- 单元测试覆盖碰撞消解、确定性、块内聚集、外围岛屿、孤立节点和三维深度边界。
- `python scripts/layout.py --algo clustered --output-dir <path>` 能在全量数据上完成并生成兼容的 `coords.parquet` 与 `report.json`。
- 全量报告显示主要块覆盖率至少 0.90，主要块投影重叠率为 0，社区 3 近邻保持率不低于 0.6。
- 抽样 10 近邻同社区比例不低于同一数据版本 `umap` 对比运行 `report.json` 记录的基线。
- `umap` 默认路径和现有测试不回归。
