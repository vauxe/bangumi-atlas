# 前端整体性能审计

本文记录 `feature/frontend-query-performance` 在查询审计之后对整个探索器继续进行的
性能分析。范围包括首屏包体与几何、相机交互、附近标签、节点详情、名称建议以及查询结果
与 Canvas 的衔接。所有保留项都以输出等价或显式误差合同为前提；完整查询执行本身见
[QUERY_PERFORMANCE.md](QUERY_PERFORMANCE.md)。

## 测量与正确性边界

- 基线 SiteRelease：`7c33b469dfcb3f4fb5f29361e6f5db7023af55493afbf325715c786827e5ac60`，
  996,459 个节点，695,446,766 字节。
- 当前 SiteRelease：`1da0d21e4bc23c6b2e0095f625669ce632259f33c7cac0df37ef9293d17f31ae`，
  节点数不变，688,446,061 字节（-7,000,705，约 -1.0%）。
- 算法基准在同一份真实数据、同一 Node 进程模型下交错运行；墙钟时间取中位数，确定性的
  访问次数、排序次数、请求字节和结果 SHA-256 才是回归门禁。
- 浏览器检查使用本机真实 Chrome、禁用 HTTP 缓存和本地 HTTP/1.1 服务。单次时间只说明
  本机趋势，不能换算为生产 CDN 或低端设备承诺。
- 查询结果、候选顺序、rank、详情字段和高亮必须精确相同。坐标是唯一允许有界误差的字段：
  manifest 声明逐轴解码参数，完整核验要求最大三维位移不越界且解码后节点不重叠。

| 冷节点邻居 rank 解析 | 172.24 ms | 约 8.26 ms | -95.2%；批量归并点查，工作集 SHA-256 不变 |

## 已保留优化

### 1. 相机、标签和选择路径不再做全量附带工作

缩放锚点只需要最近且可见的确定性候选，不需要把百万节点全部排序。当前实现用线性选择
维护同一比较规则；附近标签先应用可见性与数量边界；选中节点的冷邻居 key 则合并为一次
有序 rank 解析。查询样式更新维护实际着色 rank 集合，不再为了清理少量样式遍历完整图。

这些路径分别有工作量合同和结果等价测试。优化没有放宽标签数、邻居数、Canvas 节点数或
查询高亮上限。

### 2. 详情面板只加载实体实际引用的词表成员

旧实现打开任一实体都会读完整词表目录。现在先解码实体记录中的词表引用，再只读包含这些
引用的 gzip 成员；缺失、重复、乱序和越界引用仍会失败，不会静默省略字段。

| 实体 | 基线请求 / 字节 | 当前请求 / 字节 | 字节变化 |
|---|---:|---:|---:|
| Subject | 17 / 658,015 | 10 / 407,003 | -38.1% |
| Person | 17 / 578,536 | 4 / 58,241 | -89.9% |
| Character | 17 / 578,008 | 2 / 57,453 | -90.1% |

三个代表性实体的完整解码签名均与基线一致。

### 3. 名称建议在 Top-K 已确定后停止读取

前缀叶与内部节点都带有严格 rank 边界。当前实现只有在未读成员仍可能进入前 18 名时继续
取 Range；候选最终仍以完整规范名称或构建期别名复核，散列命中不能直接成为结果。
`境界` 的别名成员读取从 18 个降到 2 个，先把查询从 24 请求 / 3,393,167 字节降到
8 请求 / 2,429,506 字节。

### 4. 前缀和子串候选目录按需分片

旧客户端会为第一次名称查询读取 958,700 字节的完整前缀 JSON 和 1,310,752 字节的固定
子串目录。现在构建器发布两组各 16 个确定性 gzip JSON 分片：前缀按首字符 Unicode
code point 取模，子串按 65,536 个桶的桶号取模。客户端并行读取本次 query 涉及的分片，
再按精确 posting 数选择最稀有桶。

- 两类目录的发布总量从 2,269,452 降到 1,247,501 字节（-45.0%）。
- `境界` 实际只读一个 13,087 字节前缀分片和一个 59,018 字节子串分片，目录读取
  从 2,269,452 降到 72,105 字节（-96.8%）。
- manifest 强制声明全部 32 个分片；客户端逐项校验数组长度、桶号、posting 数、偏移、
  rank 边界和 gzip 上限。完整站点核验重新生成 13,778,203 条 posting，并证明它们与全部
  规范化名称等价。

### 5. 坐标传输使用逐轴仿射 u16

布局源坐标仍是 float32；发布时按每轴最小值和跨度量化成三个 little-endian u16，浏览器
流式解码进原有 `Float32Array`，因此 WebGL 缓冲、相机和标签接口不变。发布时先对完整
解码结果检查最大位移和最小节点间距，客户端再验证编码、文件长度、有限 offset/scale、
bbox 与单 rank Range。

这项优化减少网络与静态存储，不减少解码后的约 11.96 MB Float32 工作集；不能把 50%
传输收益误报为 50% 内存收益。

### 6. 查询运行时与 Canvas 启动拆分

查询工作台运行时从初始入口拆成独立 chunk。Canvas 数据请求和绘制准备不再等待查询模块
求值；空闲阶段仍可提前加载它，避免用户第一次打开查询时才承担全部网络延迟。构建同时
门禁初始入口和所有主线程 chunk，所以不会通过隐藏总包体来通过预算。

## 已撤销：三字节实体 key

曾测量把 `key.bin` 从原有 u32 改成三字节 `kind:2 + id:22`。它只减少 996,459 字节：
`key.bin` 自身 -25%，首屏几何字节约 -8.3%，完整 SiteRelease 约 -0.14%，而浏览器仍需
解码到 u32，运行时内存没有下降。更重要的是它把每类源 ID 上限从 16,777,215 降到
4,194,303，增加了迁移和长期容量风险，因此实验已完整撤销。

当前 `key.bin` 继续使用原来的 u32 `kind << 24 | id`，没有引入新的节点或源 ID 上限。
VisualRank 仍沿用既有 u24 合同；若未来总节点数接近 16,777,215，应通过新版 SiteRelease
把 rank 整体迁移为 u32，并由新旧客户端显式拒绝不兼容版本，不能依靠溢出或再次挤压
EntityKey 位宽。

## 发布验证与五轴审查

- 正确性：完整 `verify_site` 在 362 秒内通过，覆盖 996,459 个节点、全部实体/事实/分集、
  13,778,203 条名称 posting、每个 pack 成员边界和内容指纹。本次搜索目录重构前后，目录
  之外的 39 个发布逻辑文件聚合 SHA-256 逐字节相同；坐标量化另由误差和不重叠 oracle
  独立证明。
- 性能：只保留确定性工作量下降、稳定 A/B 或明确网络字节下降的改动；单次本地浏览器
  墙钟时间不作为自动门禁。
- 安全与容量：查询文本仍经原有规范化和权威字段复核；分片号来自固定模数，不能形成任意
  路径；响应、gzip 成员、解压体积、posting、节点和缓存上限均未放宽。
- 可维护性：相机、标签、邻居、词表、搜索、坐标和 bundle 分别提交，可独立回滚；格式
  常量由 Python 生产器、核验器和 TypeScript 客户端共同绑定。
- 验证：194 个 Python 测试、548 个前端测试、Ruff、格式、mypy、TypeScript、生产构建、
  688 MB 真实发布烟测和 SwiftShader WebGL 浏览器检查均通过。

## 剩余热点

1. 有排序的宽字段扫描和通用聚合仍是查询侧最大 CPU/解压热点，需要版本化列投影或二级
   索引；不能在客户端为几个示例值加入语义不完整的捷径。
2. 全局正文冷查询仍会触发数百个离散 Range。下一步收益需要重排文本成员或增加可验证的
   批量目录，同时保持权威原文复核和峰值内存上限。
3. 初始主线程 JS 已降约 15%，但 WebGL/地图依赖仍占主要代码。进一步拆分必须用真实设备
   验证首次交互，不应为了包体数字把相机所需模块延后。
4. 名称子串查询当前剩余 129,533 字节来自两个实际命中的别名成员，已经是结果正确性所需
   的权威复核数据。若继续压缩，应先重排别名成员，不能删除复核步骤。
5. 当前没有生产 RUM / CrUX；CDN 的 HTTP/2/3、多核差异、低端设备 INP 和 GPU 驱动行为
   仍需部署后的真实遥测。
