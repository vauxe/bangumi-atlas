# 前端查询性能审计

本文记录 `feature/frontend-query-performance` 对所有用户可达查询路径的审计、
基准、正确性边界、已保留优化和已撤销实验。目标不是用近似结果换速度，而是在
`QueryDocument` 和 SiteRelease 合同不变的前提下减少网络、重复计算和 DOM 工作。

## 测量边界

- 数据版本：`7c33b469dfcb3f4fb5f29361e6f5db7023af55493afbf325715c786827e5ac60`
- 数据规模：996,459 个星图实体、1,682,502 个 Episode、3,878,802 条事实，
  SiteRelease 共 695,446,766 字节。
- 本机环境：Apple M1 / 8 GB、macOS 26.3、Node 26.4.0；数据由本机
  HTTP/1.1 Range 服务提供。网络请求数和字节数可复现，墙钟时间只用于同机同条件 A/B。
- 浏览器验证：真实 Chrome；产品查询使用 Fast 4G 与 4 倍 CPU 限速，DOM 基准使用
  相同页面和强制布局，交错运行五轮后取中位数。
- 每个查询 A/B 都比较完整序列化结果的 SHA-256。哈希覆盖行、证据、列、顺序、
  `totalMatches`、`visibleMatches`、分页状态、查询摘要、发布身份、覆盖证明和终止证明。
  Canvas 高亮另以正向/反向 rank 解析等价测试保护。

冷运行表示新的 `Data` / `SiteQuerySearchIndex` 实例；热运行复用该实例的发布级索引和
有界缓存。由于生产 CDN 的协议、边缘缓存和设备不同，本地 HTTP/1.1 耗时不能直接当作
线上延迟承诺。

## 全场景审计

| 用户场景 | 实际执行路径 | 性能结论与保护 |
|---|---|---|
| 查询栏名称建议 | Subject / Person / Character 走 Canvas 名称索引，Episode 走 Query Worker；两路并行 | 90 ms 防抖、旧请求取消、最多绘制 18 条；歧义上下文才补读实体。未发现新的主线程瓶颈。 |
| 条件编辑器实体建议 | 每个 owner 并行执行结构化名称页，再按可见相关性合并 | 120 ms 防抖，异步批次逐页暴露，滚动和键盘才继续取页；取消会下传到候选和实体读取。 |
| 单类型/多类型名称查询 | 二元字符倒排候选 → rank 有序 key → 权威名称校验 → 投影实体 | 四类实体查询“命运石之门”当前冷启动 238.25 ms、热启动 8.33 ms，103 条完整结果；结果签名稳定。 |
| 属性扫描、过滤、排序、Top-N | `scanFieldRequirements` 下推必要字段；无排序有限 limit 可流式早停，有排序查询完整扫描后用有界 Top-K 堆 | `score >= 8`、按评分排序取 50：冷 3,686.95 ms / 29,440,376 字节，五次热运行中位 1,676.78 ms。仍是最大剩余热点，但内存不会按全结果集增长。 |
| 名称与正文组合 | 名称 lookup 与 full-text 分别建立精确候选，`exists` 用规范化关联列求交 | 两边都由权威源字段复核；不存在散列命中直接成为结果的路径。性能主要继承全文读取。 |
| 关系 `exists` / `notExists` | 通过锚点实体的事实邻接页展开，内层键表与外层流关联 | 不做 3,878,802 条事实的全局扫描；方向、角色、多重性和证据均保留。 |
| Episode 所属作品/反向分集 | 正向用 `episode-subject.bin` 定长点查；反向用 Subject 分区的 Episode 索引 | 避免按全部 1,682,502 个 Episode 扫描；分页游标和 owner 一致性均有合同校验。 |
| 聚合与 group-by | 扫描输入，按规范值分组；每组维护聚合状态和组证据 | 已消除每行重复提取组证据。七次强制 GC 热运行中位 3,036.00 → 1,941.58 ms（-36.0%），完整结果哈希不变。 |
| 全局正文搜索 | 五个答案分区共享发布缓存；倒排只生成候选，再读取权威文本；文本和实体批次并发上限均为 6 | “时间旅行”冷请求 814 → 729（-10.4%），字节保持 34,572,488，仍为 61 行且完整哈希相同；热运行保持 48 请求 / 7,570,608 字节。墙钟耗时处于噪声内。 |
| union / intersect / except 比较 | 每个分支按规范行键去重，集合运算合并对应证据 | 代表性比较查询约 65 ms 冷 / 16 ms 热；集合大小决定内存，输出按规范键稳定排序。 |
| 最短关系路径 | 有界 BFS，通过实体邻接事实展开；达到目标层后停止 | 代表性已缓存路径为亚毫秒级；`maxHops`、`maxPaths`、遍历角色和取消共同限制工作量。 |
| 首页、缓冲展开、Worker 后续页 | Worker 最多缓冲合同允许的页；DOM 首次只显示 50 行，之后先展开缓冲，耗尽后才请求 offset 页 | `appendQueryResultPage` 校验发布、查询摘要、覆盖摘要、总数和可见数，拒绝混页。后续 Worker 页代表性约 5 ms。 |
| 取消、替换与高亮 | `AbortController` 贯穿 UI、Worker、Range 和共享加载；硬取消会重建 Worker | 新查询只有全部分区完成后才原子替换旧结果；被取消请求无法提交。高亮发布只在 Worker 缓冲新增行时重算。 |
| 标签词表建议 | 词表 gzip 成员一次加载，内存索引按字段复用 | 已限制到两个可建议字段；排序、空查询和取消均有单测，不在当前热点前列。 |

## 已保留的优化

### 1. 复用结构化查询已经加载的实体 key

有界结构化查询本来已为名称候选加载 rank 顺序的 `key.bin`，但生成 Canvas 高亮时又会
下载 `rank-by-key.bin`。现在仅在执行计划证明结果来自可达结构 lookup 时复用已有 key；
扫描和其他不能证明的计划仍走原反向索引。

- 单次有界结构查询避免额外 3,046,152 字节下载。
- 正向 key 路径和原反向索引对同一结果产生完全一致的 rank 高亮。
- 空结果不会加载任一 rank 表，无法复用时保留原回退。

提交：`2eb2c8c perf: reuse loaded entity keys for query highlights`；发布切换审查修复：
`0c7cf71 fix: clear query key cache on release change`。

### 2. 聚合证据从“每行”降为“每组”

旧实现对每个输入行都计算 group-by 表达式证据，即使该组早已存在。现在只有创建新组时
提取一次组证据；聚合度量和行数处理完全不变。

- 落地 A/B：3,036.00 → 1,941.58 ms（-36.0%）。
- 独立复核：3,063.99 → 1,996.66 ms（-34.8%）。
- 两侧完整 `QueryResult` SHA-256：
  `97669457eff3a8695550beb48cbdb93f9f5018f91fcf7b0453aa03b3ef009e13`。

提交：`81a900d perf: avoid per-row aggregate evidence work`

### 3. 合并相邻全文 gzip 成员的 Range 读取

全文候选经常指向同一个 pack 中物理相邻的 gzip 成员。读取器现在只合并严格相邻范围，
不会下载间隙字节；临时范围租约在一个有界批次后释放，取消路径也释放租约。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 冷请求数 | 814 | 729 | -10.4% |
| 冷传输字节 | 34,572,488 | 34,572,488 | 0 |
| 结果行 | 61 | 61 | 0 |
| 热请求数 | 48 | 48 | 0 |
| 热传输字节 | 7,570,608 | 7,570,608 | 0 |

五轮交错冷运行的耗时中位为 2,406.29 ms 和 2,412.61 ms，差异处于噪声内；保留依据是
确定性的请求下降、零额外字节和相同结果哈希
`2dcf7c0748e81d7aca198453dc6c7ea37f11bdc56961b495b6c8a1f259e6d515`。

提交：`485760d perf: coalesce adjacent full-text member reads`

### 4. “继续显示”只追加新行

旧实现每次从 50 增加到 100、150……都会清空结果卡并重建此前所有行。`AnswerView`
现在仅在新结果是旧结果的不可变前缀时追加表格行或路径；行、证据、列布局或查询身份
任一变化都会保守地完整重建。计数、按钮和首行 DOM 节点得到复用，按钮焦点不会丢失。

真实 Chrome 中将 500 行分十次显示，五轮热运行结果如下：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 十次同步渲染耗时中位 | 71.7 ms | 20.9 ms | -70.9% |
| 创建元素数 | 11,069 | 2,008 | -81.9% |
| 最终表格行数 | 500 | 500 | 0 |
| 首行节点始终保留 | 否 | 是 | — |

真实产品查询还验证了 102 条结果按 50 → 100 → 102 展开，总数始终为“102 条完整结果”，
同一“继续显示”控件保持焦点。只在 Worker 真正追加缓冲页时才重新扫描 Canvas 高亮引用，
纯 DOM 展开不再遍历完整缓冲。

提交：`fbf1f61 perf: append newly revealed query rows`

## 已撤销的实验

### 合并 scan/filter/project 异步流水线

该实验把代表性扫描的 Promise 初始化数从 9,623 降到 4,819，但真实数据交错 A/B 对
执行顺序敏感：一组顺序得到 1,840 → 1,695 ms（-7.9%），反向顺序却得到基线
1,714.69 ms、候选 1,921.80 ms（候选更慢约 12.1%）。收益没有越过噪声，已完整撤销。

### 跨全文分区共享候选页 Promise

该实验能把相同倒排候选页的计算从每分区一次降为一次，但三组真实数据交错样本中，
冷中位 2,252.84 → 2,365.25 ms（+5.0%），热中位 332.52 → 339.56 ms（+2.1%）。
协调成本高于重复求交成本，已连同测试完整撤销。

## 合并前五轴审查

- 正确性：受影响场景的完整结果签名一致；分页、发布切换、不可变前缀回退和高亮双路径
  均有回归测试。审查中补上了 SiteRelease 切换时清空 rank 顺序 key 的遗漏。
- 安全与容量：未扩大查询文档、页大小、成员、pack 或缓存预算；合并 Range 仍逐个校验
  gzip 成员且不读取间隙，渲染继续只使用 `textContent`。
- 性能：只保留确定性工作量下降或越过噪声的 A/B；两个不稳定或变慢的实验已撤销。
- 可维护性：Worker、数据读取、聚合和渲染改动分别提交，可独立回滚；基准与负结果集中
  记录在本文，基准脚本纳入 TypeScript 检查。
- 测试：537 个前端测试、TypeScript 检查、生产构建和完整 SiteRelease 冒烟通过；冒烟覆盖
  199 个精确 206 Range 响应和 214 个总请求。

## 剩余瓶颈与后续方向

1. 有排序的宽扫描和通用聚合仍要解压并遍历全部 owner 实体。下一阶段应在烘焙侧增加
   版本化、可验证的查询列投影/二级索引，并让 planner 下推谓词、排序和精确计数；必须
   同时覆盖 null/missing、稳定并列顺序、distinct 和证据，不能在客户端特判几个字段。
2. 全文冷查询仍有 729 个本地 HTTP/1.1 请求。更大的收益需要重建文本成员布局或发布
   专用批量读取目录，在不增加字节和峰值内存的前提下进一步降低成员离散度。
3. 多分区查询为了不显示新旧数据混合状态，会等全部分区完成后原子替换。若要优化
   首个答案时间，应先定义“渐进展示但发布身份一致”的 UI 合同，再改提交策略。
4. 当前没有生产 RUM / CrUX。合并前仍应在实际 CDN 上复核 HTTP/2/3、低端设备 INP、
   长任务和峰值内存；本报告只把确定性工作量和同机 A/B 当作门禁。

## 复现

先构建并在一个终端启动支持 Range 的本地站点：

```sh
npm --prefix web run build
npm --prefix web run serve:smoke
```

在另一个终端运行真实数据冒烟和单场景隔离基准：

```sh
npm --prefix web run smoke
QUERY_BENCH_RUNS=7 npm --prefix web run bench:query -- lookup
QUERY_BENCH_RUNS=7 npm --prefix web run bench:query -- scan
QUERY_BENCH_RUNS=7 npm --prefix web run bench:query -- aggregate
QUERY_BENCH_RUNS=5 npm --prefix web run bench:query -- fulltext
```

`QUERY_BENCH_TEXT` 可覆盖 lookup / fulltext 的默认文本。比较提交时必须使用同一
SiteRelease、运行次数、CPU/网络条件和场景参数，并以结果签名相同为前提。
